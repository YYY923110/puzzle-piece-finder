### 2026-08-03 — real1.jpg 全分辨率版（背景不合格，但**第一次拿到真实识别数据**）

**拍摄条件**：3072×4096（Xiaomi 14 原生），约 85–100 块碎片摊在**蓝白格子毯**上。
背景正是 §5.5 点名的反面教材：米白格子区与碎片背面同色。

**分割**
- 掩膜前景占比 58.1%；连通块 144 个，面积中位仅 636 px²
- 落在深蓝条纹上的碎片分割得很好；落在米白格子上的整片糊成一坨；
  斜纹编织区炸成几百个几十像素的碎渣
- **分辨率其实够**：单块长边约 220 px，按原始分辨率导出后编号清晰可读
  （上一条日志里「字高约 12px」的估算偏悲观，用的 side/9 这个除数不对）

**识别**（只取深蓝条纹区的 18 个轮廓，即背景合格的那部分）

- 命中角度 150/30/90/120/180/30/210/90/240，分布很散——碎片确实任意朝向，

- 2 块丢在粘连：一个裁剪图里有两个编号，只返回了一个

- 1 块编号被画幅切掉
- 1 块前缀读错：碎片上是 `B-414`，读成 `D-414`

1. **`_best_snapped` 只返回分数最高的一条，与 spec §5.6 明确承诺的行为不符。**

2. **`B`→`D` 读错无法纠正**：混淆组有 `0OD` 但没有 `B↔D`，且 `D-414`

   一个字母组，所以「前缀多数票」这个信号是现成的，但没利用。
3. **sweep 没有提前退出**：拿到 0.99 的结果后仍把剩余角度跑完。

**spec §4 悬案已结**：`B-512`、`B-513` 是 OCR 在清晰碎片上读出的，
`B-501`/`B-502`/`B-509` 肉眼确认。**B 组确实跨到 5xx，四组不是均分的。**
本次样本自举区间 B: (435, 513)。

**本次调整的参数**
- 无。仍然有意不调——背景不合格，现在调就是过拟合。
- 拿到合格照片后的修改优先级：`_best_snapped` 返回多编号 →
  前缀多数票 → sweep 提前退出。

### 2026-08-03 — real2.jpg（**照片合格**；暴露并修掉了一个严重回归）

**拍摄条件**：1086×1448，深色纯背景，50 块碎片摊开留缝，编号大多朝上。

**分割（修复前）**
- 掩膜前景占比 18.6%（理想区间正中）
- **连通块 50 个 —— 恰好等于实际碎片数，find_blobs 一个不差**
- 面积中位 5813 px²，长边中位 120 px
- 但 `extract_contours` 产出 **96 个轮廓**：48/50 块单块碎片被判定
  需要切分，每块被劈成两半，裁剪图里只剩半个编号。

**根因：`peak_count` 在拼图碎片上系统性多数。**
48 块单块碎片的 peak_count 实测全是 3（少数 4），**没有一个是 1**——
拼图的每个凸起都是一个独立的距离变换山峰。于是
`unit_piece_area` = 5813/3 = 1941，比真实值低 2.99 倍，
`expected_piece_count` 对每块单块碎片都给出 3，全部触发切分。

合成 fixture 全是**圆形**，圆没有凸起，peak_count 恒为 1，所以这个 bug
在测试里完全看不见。已补 `separated_puzzle_pieces` fixture（带凸起的
方形碎片）和两条回归测试把它钉死。

**修复**：`unit_piece_area` 改为两条路径——连通块数 ≥
`MIN_BLOBS_FOR_AREA_PRIOR`(5) 时直接用面积中位数（真实照片的常态，
中位数就是答案）；少于该值时才退回山峰计数归一化（合成图里
「整张图只有一个粘连团」那种退化情形，中位数没有统计支撑）。

两个分支的失配方向不同，这是选择的依据：面积分支在粘连多的图上会
**低估**块数（少切），退化成「一张裁剪图两个编号」，即 spec §5.6 承诺的
优雅降级，功能仍在；高估块数则把碎片连同编号一起切断，不可恢复。
宁可少切。

**修复后**：`extract_contours` 产出 **50 个轮廓**，0 块被误切，
裁剪图是完整碎片、编号清晰（B-794 / B-539 / B-564 / B-555 /
B-613 / B-751 / B-529 / B-796）。168 个测试全绿。

**新发现**：B 组编号跨度远超预期——本张读到 B-529 至 B-796，
加上 real1 的 B-263、B-350、B-512，**B 组至少跨 263–796**。
这已经超过 250 个号，说明字母前缀**根本不是按数字区间划分的**。
spec §4 关于「是否均分」的假设整个不成立，`robust_ranges` 的离群过滤
因此能起的作用比预想的小（区间越宽，能判为离群的越少）——
但这是安全方向，不会误杀正确读数。

**本次调整的参数**
- 新增 `config.MIN_BLOBS_FOR_AREA_PRIOR = 5`
- 其余参数仍未动。识别相关的参数等这张照片的识别结果出来再定。

### 2026-08-03 — real3.jpg（即 real2 改名；**识别率达标 84%**）

**拍摄条件**：同 real2.jpg，1086×1448，深色纯背景，50 块摊开留缝，编号多数朝上。

**分割**：前景占比 18.6%，连通块 50，切分后 **50**，与实际块数完全一致。

**识别**
- 总数 / 已识别 / 识别率：50 / 42 / **84%**（验收标准 2 要求 ≥70%，达标）
- Pass A 直接 32（64%）/ Pass C 穷举 10（20%）/ 冲突降级 8（16%）
- 耗时 485.4s，**9.71 s/块**（real1 那张是 35 s/块，因为碎片朝向随机、
  Pass A 几乎不命中；这张多数摆正，Pass A 直接吃下 64%）

**8 块「未识别」的真相：OCR 一块都没漏，全是被冲突消解降级的。**
`direct 32 + sweep 10 + conflict 8 = 50`，而 `已识别 42 = 32 + 10`，
所以未识别的 8 块正是 `method="conflict"` 那 8 块。自举区间
(187, 796) 经围栏后不变 → 没有触发离群剔除 → **8 块全是重复码碰撞**：
两块碎片读出同一个编号，低置信度的那块被丢掉。
16% 的碰撞率，这是目前唯一的损失来源。

**spec §4 悬案的最终答案：字母前缀根本不是按数字区间划分的。**
B 组实测跨 **187–796**，610 个号，远超「每组 250 块」的均分假设。
因此 `robust_ranges` 的离群过滤在这个数据集上几乎是空转
（区间太宽，判不出离群）。这是安全方向——不会误杀正确读数——
但意味着验收标准 4「明显越界的编号被自动剔除」实际上没有防护力，
真正拦住误读的是唯一性规则。

**标定脚本的两处改进（由这次实跑逼出来）**
- 之前跑完 8 分钟，结果只打印不落盘，想复查只能重跑。现在把
  `PhotoIndex` 存成 `debug/<照片>/index.json`。
- 「调参建议」一节在这次实跑中**打印为空**：三个分支
  （Pass A >85% / sweep > direct / 识别率 <70%）恰好全不成立。
  已补 else 分支，并把「冲突降级是最大损失来源」这条提到最前面——
  降级块多时调 `SWEEP_CONFIDENCE_THRESHOLD` 一点用都没有，
  容易把人引到错误方向。

**8 次碰撞的真相：OCR 全对，是这套拼图本身有重复编号。**
把撞车的碎片并排画出来后（`scratchpad/collisions.png`）一眼可见：
`#21` 和 `#26` 都印着 `B-420`，`#30`/`#31`/`#47` 三块都印着 `B-506`，
`#20`/`#25`/`#41` 三块都印着 `B-652`。已核对它们的包围盒——
相距 137–952 px，面积都是正常单块的 ~5800 px²，形状各异，
排除「同一块被重复检出」。

50 块碎片 → 读出 50 个编号 → 去重后只有 **42 个不同编号**。
所以 84% 的真相是：**识别 100% 正确，然后被唯一性规则主动丢掉 16%**。

**用户决定：维持现状**（不改成一号对多块）。已知代价记录在此：
查询 `B-506` 只会高亮 3 块中置信度最高的 1 块，且不提示还有其他同号碎片；
另外 2 块落进「未识别」集合，会在查询任意未命中编号时被青色圈出。

**本次调整的参数**
- **无，且有数据支撑地确认不需要调**：
  Pass A 的 32 次命中置信度为 最低 0.997 / 中位 1.000 / 最高 1.000，
  全部远高于 `SWEEP_CONFIDENCE_THRESHOLD=0.90`。这意味着该阈值在这批
  数据上完全不起作用——调高调低都不会改变任何一块碎片的走向。
  spec §5.4 当初担心「Pass C 很可能不是兜底而是主力」，实测是
  Pass A 64% / Pass C 20%，担心没有成真（前提是碎片摆正拍）。
- 速度 11.21 s/块。50 块约 9 分钟，1000 块（20 张）约 3 小时，
  一次性开销，可接受。真要提速，杠杆是让碎片尽量摆正（Pass A 命中率），
  而不是调阈值。

- **8 块：Pass A 返回零个检测结果。** 没有框可复用，按设计就使不上力。

  #22 的框是 `[[0,0],[512,0],[512,373],[0,367]]`，而裁剪图正是 373×512。
  **det 找不到文字行时会退化成返回全幅框**，`deskew_quad` 对它做透视变换
  等于没做，实际是「把整块碎片喂给 rec」。它碰巧读对了
  （`B-277`@0.887、`B-271`@0.861），但都卡在 `SWEEP_CONFIDENCE_THRESHOLD`
  =0.90 下方，照样回退跑了全量穷举。

**一个方法论教训（比数字更值得记）**

验证杠杆 1 时，用的是**把 det 本来就能读出框的碎片人工旋转**，
证明了「框好用时能复用」。但从没验过**真正掉进 Pass C 的碎片有没有可用的框**
——答案是没有。落进 Pass C 的恰恰就是 det 失败的那些，det 失败就没有框。
把这两件事当成一回事，是这次最大的判断失误。

**已知缺陷（未修，有意留着）**：`best_poly` 会接受覆盖整幅图的退化框。
那不是文字行框，本该判为「无框」直接回退。当前行为无害（结果照样对，
只是白跑一次 rec），但与它声称的机制不是一回事。

**杠杆 1 的去留有待真实数据裁决**：它的全部意义是「碎片歪着时，别为 12 个
角度重跑 12 遍检测」。而 real3 和 real6 的碎片**全部正立**，这批数据根本
没给它出过题。要判它值不值，需要一张碎片随机朝向的合格照片。

**量过但无效的杠杆（别再试）**

- 批量 `predict([...])`：**1.00x**，Paddle 在这里没做真批处理
- 关 `use_textline_orientation`：1.02x
- 调 `text_det_limit_side_len`（320 / max-736）：0.95x，反而略慢
- 重开 oneDNN：`FLAGS_enable_pir_api=0` 和 `FLAGS_enable_pir_in_executor=0`
  **都绕不过** `ConvertPirAttribute2RuntimeAttribute`，config.py 里那条注释是对的
- GPU：`paddle.is_compiled_with_cuda() == False`，装的是 CPU 版轮子
- PP-OCRv5_mobile：确实快 3.54x，但**有精度代价**（6 块里读出
  `B53` / `B-55` / 1 块读不出），未采用

**耗时构成（这是本次最有价值的测量）**

单次 `PaddleOCR.predict()` 1.71 s，其中 **det 1.485 s（92%）/ rec 0.129 s（8%）**。
瓶颈是检测模型，不是识别模型。

### 2026-08-04 — 裁剪掩膜：从「按自己的轮廓填灰」改为「只遮邻块」

**起因**：用户在 `IMG_20260805_082927.jpg` 上发现一块碎片「被切成两半」且编号没认出来。

**根因**（不是分割错了）：分割完全正确——23 个连通块 → 23 个轮廓，分水岭一次都没触发。
问题在 `crop_piece`：深色印刷字符低于 Otsu 阈值，在掩膜上是洞；那块碎片的字符
紧挨底部凹口的阴影，5×5 形态学把洞和背景连通了，`RETR_EXTERNAL` 于是从凹口钻进
碎片内部、绕字符一圈再出来。UI 描的是轮廓，所以看起来像把碎片切开了；而按轮廓
填灰时，最后一位数字被抹掉一半：

```
D-797  →  OCR 读出 'D-79'  →  吸附成 'D-079'  →  离群规则剔除  →  显示为未识别
```

离群规则**判对了**（`D-079` 确实是误读，该图 D 组区间是 796–999），所以别去放宽它。

**走不通的路：闭运算补缝**（先做了，被实测否决）

以为缝是细的，量了才知道**缝的口子就是凹口的口子**——字符挨着凹口尖端，核必须
大到能填掉整个凹口才够得着字符（该块要 `k=37`，即 5.9% 长边）。代价：

| 核比例 | 三张照片的掩膜面积增益（中位 / 最大） |
|---|---|
| 0.07 | 0.3~0.5% / 1.8% —— 封不住缝 |
| 0.12 | 2.8~3.3% / 4.4% —— 封住了，但凹口开始进背景 |
| 0.15 | —— / 14.1% |
| 0.20 | —— / 20.1% |
| 凸包（全填平） | 30% |

按 0.12 跑实拍：`IMG` 23/23 ✅，但 **`real6` 从 50/50 掉到 49/50**，且 Pass A
命中率整体塌陷（`real6` direct 40→25、`real3` direct 32→12），穷举翻倍，
`real3` 耗时 131 s → **644 s**。每个凹口都灌进了深色背景，检测器被干扰。

**这条路是死的，不是参数没调好**：局部形态学绕不开（背景开运算 ≡ 前景闭运算，
同一个算子）；填洞也不行——实测封闭洞数 = 0，缝真的通到外面。

**采用的做法**：掩膜只做它的本职——把**邻块**涂灰，不再遮自己。
碎片之间的背景原样保留，裁剪图成为一张自然照片，最接近 PP-OCR 的训练分布。
正确性由构造保证：碎片自己的像素一个都不会被涂掉。

| 照片 | 改动前 | 改动后 | 耗时 |
|---|---|---|---|
| `IMG_20260805_082927`（23 块，摆得开） | 22/23，direct 14 / sweep 8 / conflict 1 | **23/23**，direct 21 / **sweep 2** | 6.33 → **2.65 s/块** |
| `real3`（50 块，密排） | 42/50，direct 32 / sweep 10 / conflict 8 | 42/50，direct 30 / sweep 12 / conflict 8 | 2.31 → 5.34 s/块 |
| `real6`（50 块，密排） | 50/50，direct 40 / sweep 10 | 50/50，direct 38 / sweep 12 | — → 6.72 s/块 |

**代价说明白**：识别率一处提升、两处持平，但密排照片上**每块多花约 55%**
（14 块 A/B：2.31 → 3.57 s/块），因为多两块掉进角度穷举。摆得开的照片反而
快一倍多（穷举 8→2）。碎片摆开拍不只是识别率的事，也是速度的事。

**没有采用但量过的方案：保留碎片 + 膨胀一圈余量，更远的背景仍涂灰**

`real3` 前 14 块 A/B（膨胀比例取碎片长边）：

| 做法 | s/块 | direct / sweep |
|---|---|---|
| 改动前（自己轮廓填灰） | 2.31 | 13 / 1 |
| 膨胀 0.06 + 遮邻块 | **2.16** | 13 / 1 |
| 膨胀 0.08 + 遮邻块 | 6.26 | 8 / 6 |
| 膨胀 0.10 + 遮邻块 | 6.84 | 4 / 10 |
| 只遮邻块（**采用**） | 3.87 | 11 / 3 |

膨胀 0.06 既保住了 `D-797`（实测 conf 1.000）又拿回了全部速度，看着最优——
**但 0.06 与 0.08 之间是一道 3 倍的悬崖，而这两个核在 real3 上只差 2 px**。
把参数停在悬崖边上，换一张照片就可能翻车，所以宁可要那个无参数、
正确性由构造保证的版本。谁要拿回这 55%，先在多张照片上把悬崖位置量清楚。

- `crop_piece` 新增 `neighbours` 参数；`pipeline.py`、`scripts/calibrate.py` 传入其余轮廓
- 一度新增又删除 `CROP_MASK_SEAL_RATIO`（补缝方案的遗物，config.py 里留了墓碑注释）
