# 调参日志 —— 结论与禁区

**这份文档回答一件事：改参数之前，你需要知道哪些已经被实测否决过。**

原始的逐张照片流水账（2026-08-03 至 08-04，七次实拍/合成图标定）已从文档里移除，
因为那些照片本身不入库（见 `.gitignore`）、本地也已清空，逐条复述拍摄条件对
「现在该怎么调参」没有帮助。**下面每一条结论都来自真实测量，但都无法在当前
仓库里重跑复现**——要重新验证，得重新拍照标定。完整流水账在 git 历史里
（`git log --follow docs/tuning-log.md`）。

---

## 1. 输入条件决定成败，调参救不回

这是全部结论里最重要的一条。三次实拍的教训：

| 条件 | 实测后果（违反时） |
|---|---|
| **深色纯背景** | 蓝白格子毯：米白格子区与碎片背面同色，碎片整片糊成一坨；斜纹编织区炸出几百个几十像素的碎渣。18 个轮廓里 **7 个根本不是碎片** |
| **摊开留缝** | 40 块只形成 14 个连通块；粘连的碎片被当成一块，一张裁剪图里两个编号只返回一个 |
| **一张 40–60 块** | 决定每个字符占多少像素 |
| **导出别缩图** | 缩到 905×933 后单块长边 112 px → 字符高约 12 px，**任何参数都救不回来** |
| **编号尽量朝正** | 朝向随机时 **35 s/块**（Pass A 几乎不命中，每块跑满 12 个角度）；摆正后 Pass A 直接吃下 64% |

**分辨率的可用下限**：单块包围盒长边 ≥250 px。实测 220 px 时编号仍清晰可读，
112 px 时肉眼都读不全。

自查方法：跑完 `scripts/calibrate.py`，看 `debug/<照片名>/crops/` 里的图——
编号必须清晰可读，且一张图里只有一个编号。

## 2. 分割

**已修的严重回归：`peak_count` 在拼图碎片上系统性多数。**
实测 48 块单块碎片的 peak_count **全是 3**（少数 4），没有一个是 1——拼图的每个
凸起（tab）都是一个独立的距离变换山峰。于是 `unit_piece_area` 被压低 2.99 倍，
48/50 块单块碎片被判定需要切分，50 块碎片产出 96 个轮廓，**每块被劈成两半、
裁剪图里只剩半个编号**。

合成 fixture 全是**圆形**，圆没有凸起，peak_count 恒为 1，所以这个 bug 在测试里
完全看不见。已补 `separated_puzzle_pieces` fixture（带凸起的方形碎片）和两条回归
测试钉死它。**别再把分割测试只建立在圆形上。**

**修法与依据**：`unit_piece_area` 分两条路——连通块数 ≥ `MIN_BLOBS_FOR_AREA_PRIOR`(5)
时直接用面积中位数（真实照片的常态，实测 50 块碎片恰好形成 50 个连通块，面积紧紧
聚在中位数附近）；少于该值时才退回山峰计数归一化。

**选择的依据是失配方向不同**：面积分支在粘连多的图上会**低估**块数（少切），
退化成「一张裁剪图两个编号」，即 spec §5.6 承诺的优雅降级，功能仍在；
高估块数则把碎片连同编号一起切断，**不可恢复**。宁可少切。

**其他已知行为**

- `split_blob` 二分搜不到恰好 expected 个种子时，整体回退成「不切」。实测期望 32 块
  时一个都切不出来，巨型团块原样穿过。这是安全方向。
- 分割本身**完全不是瓶颈**：50 块 12 ms，OCR 才是全部成本。
- 未采纳的替代信号：`area / dtmax²` 在单块碎片上是 5.78–9.35（中位 7.09）、
  在粘连团上是 10.6–26.8，两者分得很开，可能比山峰计数更稳健；但对大团块失效
  （重叠会让 dtmax 变大），需要合格照片重新评估。

## 3. 裁剪掩膜：只遮邻块，绝不遮自己

**起因**：一块碎片在界面上「被切成两半」，编号也没认出来。

**根因不是分割错了**——23 个连通块 → 23 个轮廓，分水岭一次都没触发。
问题在 `crop_piece`：深色印刷字符低于 Otsu 阈值，在掩膜上是洞；那块碎片的字符
紧挨底部凹口的阴影，5×5 形态学把洞和背景连通了，`RETR_EXTERNAL` 于是从凹口钻进
碎片内部、绕字符一圈再出来。UI 描的是轮廓，所以看起来像把碎片切开了；而按轮廓
填灰时，最后一位数字被抹掉一半：

```
D-797  →  OCR 读出 'D-79'  →  吸附成 'D-079'  →  离群规则剔除  →  显示为未识别
```

离群规则**判对了**（`D-079` 确实是误读，该图 D 组区间是 796–999），别去放宽它。

### 走不通的路：闭运算补缝

以为缝是细的，量了才知道**缝的口子就是凹口的口子**——字符挨着凹口尖端，核必须
大到能填掉整个凹口才够得着字符（实测该块要 `k=37`，即 5.9% 长边）。代价：

| 核比例 | 三张照片的掩膜面积增益（中位 / 最大） |
|---|---|
| 0.07 | 0.3~0.5% / 1.8% —— 封不住缝 |
| 0.12 | 2.8~3.3% / 4.4% —— 封住了，但凹口开始进背景 |
| 0.15 | —— / 14.1% |
| 0.20 | —— / 20.1% |
| 凸包（全填平） | 30% |

按 0.12 跑实拍：那张 23 块的达到 23/23 ✅，但**另一张 50 块的从 50/50 掉到 49/50**，
且 Pass A 命中率整体塌陷（direct 40→25、另一张 32→12），穷举翻倍，耗时 131 s → **644 s**。
每个凹口都灌进了深色背景，检测器被干扰。

**这条路是死的，不是参数没调好**：局部形态学绕不开（背景开运算 ≡ 前景闭运算，
同一个算子）；填洞也不行——实测封闭洞数 = 0，缝真的通到外面。

### 采用的做法与代价

掩膜只做本职：把**邻块**涂灰。碎片之间的背景原样保留，裁剪图成为一张自然照片，
最接近 PP-OCR 的训练分布。**正确性由构造保证：碎片自己的像素一个都不会被涂掉。**

| 照片 | 改动前 | 改动后 | 耗时 |
|---|---|---|---|
| 23 块，摊得开 | 22/23，direct 14 / sweep 8 / conflict 1 | **23/23**，direct 21 / **sweep 2** | 6.33 → **2.65 s/块** |
| 50 块，密排 | 42/50，direct 32 / sweep 10 / conflict 8 | 42/50，direct 30 / sweep 12 / conflict 8 | 2.31 → 5.34 s/块 |
| 50 块，密排 | 50/50，direct 40 / sweep 10 | 50/50，direct 38 / sweep 12 | — → 6.72 s/块 |

**代价说明白**：识别率一处提升、两处持平，但密排照片上每块多花约 **55%**
（14 块 A/B：2.31 → 3.57 s/块），因为多两块掉进角度穷举。摊得开的照片反而快一倍多。

### 量过但没采用：保留碎片 + 膨胀一圈余量

密排照片前 14 块 A/B（膨胀比例取碎片长边）：

| 做法 | s/块 | direct / sweep |
|---|---|---|
| 改动前（自己轮廓填灰） | 2.31 | 13 / 1 |
| 膨胀 0.06 + 遮邻块 | **2.16** | 13 / 1 |
| 膨胀 0.08 + 遮邻块 | 6.26 | 8 / 6 |
| 膨胀 0.10 + 遮邻块 | 6.84 | 4 / 10 |
| 只遮邻块（**采用**） | 3.87 | 11 / 3 |

膨胀 0.06 既保住了那个编号（实测 conf 1.000）又拿回了全部速度，看着最优——
**但 0.06 与 0.08 之间是一道 3 倍的悬崖，而这两个核在那张照片上只差 2 px**。
把参数停在悬崖边上，换一张照片就可能翻车，所以宁可要那个无参数、正确性由构造
保证的版本。谁要拿回这 55%，先在多张照片上把悬崖位置量清楚。

## 4. 识别与提速

**耗时构成（最有价值的一次测量）**：单次 `PaddleOCR.predict()` 1.71 s，
其中 **det 1.485 s（92%）/ rec 0.129 s（8%）**。瓶颈是检测模型，不是识别模型。

### GPU：34.2x，代码零改动（2026-08-05）

**这是本项目至今最大的一笔提速，而且它推翻了 spec §5.10 当初否决 GPU 的理由。**

同一张 `real7.jpg`（50 块密排 1086×1448），`scripts/benchmark.py` 前后各跑一次：

| | 总耗时 | 每块 | 识别率 | 走向 |
|---|---|---|---|---|
| CPU（`CUDA_VISIBLE_DEVICES=""` 藏掉显卡） | 246.4 s | 4.928 s | 50/50 | direct 39 / sweep 11 |
| **GPU**（RTX 3050 Laptop 4GB） | **7.2 s** | **0.144 s** | 50/50 | direct 39 / sweep 11 |

**50 个编号逐条相同**（程序比对，不是肉眼），方法分布也一致。纯提速，零精度代价。
CPU 那一行是用 GPU 版轮子藏掉显卡跑的——同一个 wheel、同一份模型，对照才干净。

**当初否决的理由（「本机是 CUDA 13，很新，大概率未覆盖」）是错的。** 官方源上
`cu130` 通道有 `paddlepaddle_gpu-3.3.1-cp313-cp313-win_amd64.whl`，版本、Python、
平台三样全对得上原来装的 CPU 版，不用降级任何东西。

**比版本更关键的一点变化**：CUDA 运行时和 cuDNN 现在是**普通 pip 依赖**
（`nvidia-cuda-runtime` / `nvidia-cudnn-cu13` / `nvidia-cublas` 等），
`pip install` 一并拉下来。历史上 Windows 装 Paddle GPU 要自己装几个 GB 的
CUDA Toolkit 再配 cuDNN，那道坎没了。总下载约 1.9 GB。

**代码一行没改。** `paddleocr._constants.DEFAULT_DEVICE` 是 `None`，
即自动选择；paddle 编进了 CUDA 且检测到显卡时直接走 `gpu:0`。
`enable_mkldnn=False` 留着无害——它是 CPU 专属参数，GPU 上空转，
而它防的那个 PIR 算子缺口在 GPU 上根本不存在。

**一个安装陷阱，已在 `pyproject.toml` 里修掉：** `paddlepaddle` 和
`paddlepaddle-gpu` 是两个发行名、抢同一个 `paddle` 包目录。原来 `paddlepaddle`
写在主依赖里，实测 `pip install --dry-run -e .` 会 `Would install paddlepaddle-3.3.1`
——GPU 装好之后随手重跑一次安装命令，34 倍就无声无息地没了。现已拆成
`[cpu]` extra，装漏了会当场 ImportError。**响亮的失败好过安静的退化。**

**实测 2.94x（385 s → 131 s，编号一个不丢一个不多），全部来自
`SWEEP_EARLY_EXIT_CONFIDENCE = 0.99`**：穷举时拿到 ≥0.99 的合法编号就收工。3 行改动。

**「复用检测框、只重跑 rec」（`LineOcrBackend`）至今一次都没生效。**
代码保留着，但**没有被真实数据验证过**。逐块查过 50 块，走 Pass C 的 10 块分两类：

- **8 块：Pass A 返回零个检测结果**，没有框可复用，按设计就使不上力
- **2 块：有「框」，但那个框是整张裁剪图**（`[[0,0],[512,0],[512,373],[0,367]]`
  而裁剪图正是 373×512）。det 找不到文字行时会退化成返回全幅框

> **一个方法论教训，比数字更值得记。** 验证这条杠杆时，用的是**把 det 本来就能
> 读出框的碎片人工旋转**，证明了「框好用时能复用」。但从没验过**真正掉进 Pass C
> 的碎片有没有可用的框**——答案是没有。落进 Pass C 的恰恰就是 det 失败的那些，
> det 失败就没有框。把这两件事当成一回事，是整个改造里最大的判断失误。

它的去留有待真实数据裁决：全部意义是「碎片歪着时别为 12 个角度重跑 12 遍检测」，
而已标定的那几张碎片**全部正立**，这批数据根本没给它出过题。要判它值不值，
需要一张碎片随机朝向的合格照片。

### 量过且确认无效，别再试

- 批量 `predict([...])`：**1.00x**，Paddle 在这里没做真批处理
- 关 `use_textline_orientation`：1.02x
- 调 `text_det_limit_side_len`（320 / max-736）：0.95x，反而略慢
- 重开 oneDNN：`FLAGS_enable_pir_api=0` 和 `FLAGS_enable_pir_in_executor=0`
  **都绕不过** `ConvertPirAttribute2RuntimeAttribute`，`config.py` 里那条注释是对的。
  （这条只对 CPU 有意义，GPU 上不涉及）
- PP-OCRv5_mobile：确实快 3.54x，但**有精度代价**（6 块里读出 `B53` / `B-55`、
  1 块读不出），未采用

> 「GPU：装的是 CPU 版轮子」这条曾经在本清单里。那不是一次评估，只是对当时
> 安装状态的陈述，被误当成结论了。实测见上，34.2x。**别把「现状如此」写成
> 「试过不行」**——这是本文档踩过的一个记录方式上的错。

### 还没动的杠杆

**先说结论：在 GPU 上这些基本都不值得做了。** 50 块 7.2 秒，下面两条都是在
7 秒上做文章，各自带来一堆复杂度。只有在没有显卡、退回 CPU 时才重新有意义。

- **多进程**：CPU 单进程实测占 7.9 / 16 逻辑核，还剩一半空闲，估计还有 ~1.7x
- **彻底绕开 det**（用 OpenCV 自己定位那行浅灰字）：CPU 上理论 13x，但是新的
  调参战场。spec §5.4 当初否决过「自行估计文字角度」，理由是调参成本高——
  那个否决的前提是「det 免费」，det 占 92% 之后前提一度变了；**而 GPU 把 det
  变回了几乎免费，这条又该躺回否决区**。

## 5. 编号、词表与消解

**字母前缀不是按数字区间划分的。** B 组实测跨 **187–796**（610 个号），远超「四组
均分、每组 250 块」的假设。因此 `robust_ranges` 的离群过滤在真实数据上几乎空转
（区间太宽，判不出离群）。这是安全方向——不会误杀正确读数——但意味着
「明显越界的编号被自动剔除」实际上没有防护力，真正拦住误读的是**唯一性规则**。

**同一个编号会印在多块碎片上，这是拼图本身的性质，不是 OCR 错了。**
一张 50 块的照片读出 50 个编号，去重后只有 **42 个不同编号**：`B-506` 和 `B-652`
各出现在 3 块上，`B-420` 出现在 2 块上。已核对包围盒（相距 137–952 px）、面积
（都是正常单块的 ~5800 px²）和形状，排除「同一块被重复检出」。

所以那张照片 84% 的真相是：**识别 100% 正确，然后被唯一性规则主动丢掉 16%**。
维持现状是权衡后的决定，代价见 README「已知限制」。

**`SWEEP_CONFIDENCE_THRESHOLD` 在合格照片上完全不起作用。**
Pass A 命中时的置信度实测最低 0.955、中位 1.000，全部远高于阈值 0.90——
调高调低都不会改变任何一块碎片的走向。**降级块多时去调它一点用都没有**，
容易把人引到错误方向；该看的是冲突降级数。

**前缀读错纠正不了**：混淆组里有 `0OD` 但没有 `B↔D`，而 `D-414` 本身是合法
编号，词表吸附和区间过滤都拦不住。一张照片只摊一个字母组，所以
「前缀多数票」是现成的信号，但**目前没有利用**。

**real7 给了这条一份干净的实证（2026-08-05）。** 那张 50 块读出的编号是
`A-250` + `B-251…B-299`——连续区间显然应该是 `B-250…B-299`，那个 `A-250`
是 `B-250` 的前缀误读。它躲过了每一道防线：格式合法、吸附无话可说、
唯一性不冲突、区间过滤只看数字不看字母。**CPU 和 GPU 读出的是同一个错**，
所以不是硬件差异，是模型在这块碎片上就这么认的。

一整张图 49 个 B、1 个 A，多数票会直接改对。这是目前手上唯一一张能验证
该规则的照片，**要做的话记得先想清楚失配方向**：真有人把两个字母组摊在
同一张照片上时，多数票会把少数派那组全部改错——那比现在这一个错更糟。

- `best_poly` 会接受覆盖整幅图的退化框。那不是文字行框，本该判为「无框」直接回退。

## 7. 记录下一次实拍

标定跑完在文末追加一条，格式随意，但**至少要有**：

- **拍摄条件**：分辨率 / 背景 / 碎片数 / 单块包围盒长边
- **分割**：连通块数 / 切分后轮廓数 / 实际碎片数（三者对不上就是分割问题）
- **识别**：总数 / 已识别 / `direct`·`sweep`·`line`·`conflict` 各多少 / 每块耗时
- **改了哪个参数，为什么**——没改也要写「无，且有数据支撑地确认不需要调」

**参数只在有实测数据支撑时才动。** 对着一张违反前提的照片调参就是过拟合，
历史上有意跳过了两次。

## 8. 实拍记录

### real7.jpg — 2026-08-05

- **拍摄条件**：1086×1448，深色纯背景，50 块密排，单块包围盒长边中位 **132 px**
- **分割**：50 个轮廓 / 实际 50 块，零偏差（面积中位 7930 px²）
- **识别**：50/50（100%），`direct 39 / sweep 11 / line 0 / conflict 0`
- **耗时**：GPU **0.144 s/块**（7.2 s），CPU 4.928 s/块（246.4 s），**34.2x**
- **改了哪个参数**：无。这一轮动的是**运行环境**（换 GPU 版 paddle），
  不是参数；识别结果逐条不变，正说明没有任何参数需要跟着动。
- **两个新发现**：`A-250` 前缀误读（见 §5）；`pip install -e .` 会把 CPU 版
  paddle 装回来、无声吃掉 34 倍（见 §4，已修）

> **单块长边 132 px，低于 §1 写的「可用下限 ≥250 px」，却拿到了 100%。**
> 别据此放宽那条下限——132 px 是这张照片的**包围盒**长边，而 §1 那个 250 px
> 的教训来自一张被缩图的照片，字符高度只剩 12 px。真正决定成败的始终是
> **字符占多少像素**，包围盒只是它的粗代理，而裁剪时会放大到
> `CROP_TARGET_LONG_EDGE`。要改下限，得直接量字符高度。
