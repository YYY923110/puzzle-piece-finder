# 设计说明 —— 为什么是这样做的

这份文档回答「为什么」。**上手用法看 [README](../README.md)。**

每一节都记着被否决的替代方案。它们不是没想到，是想过之后主动放弃的。

---

## 1. 问题

一套 1000 块的拼图，每块背面印着 `一个大写字母 + 短横 + 数字`，数字**不补零**
（`A-1` / `B-403` / `D-1000`）。四个字母各占一段互不重叠的区间：
A 为 1–260，B 为 261–520，C 为 521–760，D 为 761–1000，合计正好 1000，
与碎片数一一对应。**这条性质到项目后期才确定，它比看上去重要**——见 §6.4。
拼的过程中要找某一块，桌上散着几百块，肉眼逐块翻找极其低效。

**真正的目标不是「在屏幕上标出碎片」，而是「让用户的手能在桌上找到它」。**
屏幕只是中介。这条洞察决定了高亮的设计（§7）。

---

## 2. 建索引 + 查表，而不是每次现拍现认

拍一次照建立完整索引，之后查询走本地查表，毫秒级返回。

识别是重活——几十上百块碎片的分割加 OCR。这个成本必须摊销，不能放在
延迟敏感的查询路径上。

代价是索引会过期：拼图是动态的，拿走一块索引就部分失效。缓解手段是分块
拍照（§5），让刷新单张照片的成本低到用户愿意去做。索引带时间戳供界面提示。

---

## 3. 为什么不用视觉大模型

**否决一：整图直接交给视觉模型。** 一张图里上百个微小的、任意旋转的、
浅灰低对比的文本，是这类模型最弱的场景。而且它不产出碎片轮廓，拿不到
坐标就没法高亮——而高亮才是这个工具的全部意义。

实证：项目早期真的这么试过一次，读出的编号里混着一批系统性误读。

**否决二：分割后逐块交给视觉模型。** 技术上可行，成本也低。这条是主动
放弃的，理由是全本地、免费、离线、可无限次迭代不心疼。风险因此从「花钱」
转移到「花时间调参」，缓解手段是把识别器做成可替换的协议接口（§9），
撞墙时换后端不用重写整条链。

**否决三：学习型分割（SAM 等）。** 对背景免疫，但几百 MB 模型加显著推理
时间，对一个拼图辅助工具是杀鸡用牛刀。

---

## 4. 深色纯背景：用 30 秒的行为改变换掉一整天的调参

这是整个设计里性价比最高的一条。

要求用户把碎片摊在深色纯背景上，前景分离就退化成一次 Otsu 阈值操作。
反例是真实踩过的：蓝白格子毯上，米白色格子与碎片背面几乎同色，
任何基于颜色的阈值都分不出来，而那一带正压着十几块碎片；斜纹编织区
还炸出几百个几十像素的假轮廓。

**否决：支持任意背景。** 需要自适应阈值加边缘辅助加纹理特征，每一项都是
要试的参数，换个光线可能又要重调。把这个负担丢给用户的一块深色桌布，
是明显更划算的交换。

---

## 5. 一张照片 40–60 块

决定识别率的不是照片总像素数，而是**每个字符占多少像素**——PP-OCR 会把
文字行统一缩放到固定高度，源图字符太小就等于喂给模型一张糊图。而字符
像素数由「一张塞多少块」决定：

| 一张拍多少块 | 每块约占 | 字符高度 | 处境 |
|---|---|---|---|
| 250（一整组） | ~250 px | ~15 px | 勉强，大概率掉识别率 |
| 100 | ~400 px | ~25 px | 及格线 |
| 50 | ~570 px | ~35 px | 舒服 |

既然放弃了大模型和 SAM 这些兜底，**剩下唯一还能提升识别率的杠杆就是给
OCR 更清楚的输入**，而这个杠杆是免费的：多按两次快门换字符像素数翻倍。

附加收益是刷新成本低。桌上正在拼的那块区域动得最频繁，其他区域可能十几
分钟没动过，只重拍变动的那一张就够了。

## 6. 识别管线

### 6.1 分割：阈值 → 连通块 → 按需切分

碎片粘连时会被当成一个连通块。切分的做法是对团块做距离变换，再二分搜索
一个阈值系数，使「距离大于系数乘最大距离」的区域恰好裂成 N 块，这些区域
作为分水岭的种子。N 由「团块面积 ÷ 全图碎片面积中位数」估计。

常规做法要手调「阈值取 0.5 还是 0.7」这类魔法系数，这里让每个团块自己找
系数，用户完全不必参与。

**切分失败是优雅降级，不是崩溃。** 两块粘连被当成一块时，裁剪图里有两个
编号，OCR 会读出两个，系统把两个编号都指向该区域——高亮范围偏大，功能仍在。
所以在「少切」和「多切」之间，实现刻意偏向少切：多切会把碎片连同编号一起
切断，那是不可恢复的。

### 6.2 裁剪：只遮邻块，绝不遮自己

每块碎片单独裁出、放大后再送去识别。裁剪图里只把**邻块**的像素涂成中性灰，
碎片之间的背景原样保留。

**为什么不按碎片自己的轮廓填灰**（这是踩过的坑）：深色印刷字符低于阈值，
在掩膜上是一个洞；字符紧挨拼图凹口时，那个洞会与外部背景连通，外轮廓便
从凹口钻进碎片内部绕字符一圈——填灰时正好抹掉半个编号。而想用闭运算补
那道缝也走不通：缝的口子就是凹口的口子，核大到够得着字符时，凹口连同
邻域的深色背景一起被灌进裁剪图，识别率反而塌一半。

现在这个做法的正确性由构造保证：**碎片自己的像素一个都不会被涂掉。**

### 6.3 旋转：直读打底，角度穷举兜底

- **Pass A** —— 整块裁剪图直接送 OCR，靠检测器自己输出旋转框并摆正。
  合格照片上这条吃下约 2/3 到 4/5 的碎片。
- **快路径** —— Pass A 拿到了检测框但读数不理想时，按框裁出文字行、
  只重跑识别模型试正反两个朝向，跳过昂贵的检测模型。
- **Pass C** —— 上面都不行就把裁剪图旋转一圈，每个角度识别一次，取最优。

穷举听起来笨，但**「必须能吸附到合法词表」这个约束让它的判据非常硬**——
错误的角度几乎不可能凑出一个合法编号，所以误报率极低。代价只是算力时间，
而建索引是一次性的。拿到足够高置信度的合法编号就提前收工。

**否决：自行估计文字角度**（对墨迹像素做 PCA 或 `minAreaRect` 求主轴）。
绕过了检测器这个单点，但阈值分离要调，碎片花纹、阴影、边缘都会污染主轴
估计。这是调参成本最高的一条，而穷举用蛮力达到了同样的效果。

### 6.4 后处理：词表吸附 + 同图消解

编号空间是 §1 那四段区间，共 1000 个候选。OCR 的原始读数先归一化
（去空白、统一各种破折号、补缺失的连字符、去掉前导零），再用一个**带形近
字符折扣的编辑距离**吸附到最近的合法编号——`0/O/D`、`1/I/L`、`8/B` 这类
替换的代价低于普通替换。

**区间互不重叠，所以数字唯一确定前缀——前缀退化成一位校验码。** 这是区间
确定之后最大的收获：`A-403` 不再是合法编号（403 属于 B 段），前缀误读
必定暴露。实测 3000 种可能的前缀误读，没有一种会被静默当成真编号收下。

但**检出不等于可纠正**，这一点必须说清楚。`A-403` 有三个等距解释：前缀错了
（`B-403`），或百位错了（`A-103` / `A-203`）。没有依据在三者间选择，于是
判为歧义、拒绝作答。实测 3000 种前缀误读里 2997 种如此，而其中**没有一种
被纠正成错误的编号**。真正兑现的收益是失败模式变了：从「悄悄读成另一个
合法编号并占掉它的位置」变成「明确的读不出」——后者由 §7 那条
「查不到时高亮全部未识别碎片」兜住，代价小得多。

不补零还带来一个副作用：编号长度在 3–6 之间浮动，于是「漏读一位数字」和
「读错前缀」经常等距（`D-97` 补成 `D-970`…`D-979` 全都说得通）。处理办法是
给增删设不对称代价——OCR 凭空多读一个字符比漏读一个字符更罕见，实测里的
失败读数 `D-97` / `D-89` / `D-83` 全是漏读，没有一例是多读——再加一条歧义
判据：最优与次优拉不开差距时一律不作答。

**吸附预算也必须随位数缩放。** `2.0` 的编辑距离预算对五字符的 `B-403` 是
「允许 40% 的字符出错」，换到三字符的 `A-1` 上就是 67%，噪声会被吸附成真编号。
现在的上限是 `min(2.0, 数字位数 × 0.7)`：三位及以上仍是 2.0（原有行为一字
未变），一位数字则只放行形近替换，读不出就是读不出，不做无依据的猜测。

**否决：从识别结果里自举区间。** 区间未知时这是唯一的办法，实现过一版
（四分位围栏 + min/max）。区间确定之后它被整段删掉，不只是因为多余：它真正
会触发的场合恰恰是误伤——一张全是 `D-9xx` 的照片里混进一块真实的 `D-762`，
围栏会把这个**对的**结果当离群值丢掉。而它本想抓的 `B-901` 现在压根不是
合法编号，在吸附那一层就进不来。

之后只剩一条全局规则：同一张照片里编号重复时只保留置信度最高的那块。

**唯一性规则现在是一条无损规则。** 1000 个编号与 1000 块碎片一一对应，
每个编号只印在一块碎片上，所以同一张照片里读出重复编号时，其中必有误读——
丢掉置信度低的那块是**纠错**，不是取舍。

这一条曾经写成「有损规则」：早期实测以为同一编号会印在多块碎片上，因而
认为该规则会主动丢弃真实存在的碎片。区间确定之后可以断定，那个观察本身
就是一次误读。**这是编号区间带来的第二个收获**——它把一条当初含糊接受的
妥协，变成了一条有依据的规则。

## 7. 高亮：克制的压暗，而不是全黑

非目标区域压暗到约 45% 亮度，目标碎片保持原亮度并用高饱和洋红描边，
同时显示识别到的编号和该碎片的裁剪缩略图。放大是可选按钮，不自动触发。

压暗比单纯描边强得多——一张图里上百块碎片，一圈红边会被视觉噪声淹没。
但**压得太暗会破坏空间定位能力**：用户把屏幕位置映射到桌面真实位置，靠的
是周围碎片的排布、背景纹理、桌沿这些参照物。压成全黑或自动缩放到极致，
用户会知道「它在这儿」却不知道「这儿是哪儿」。45% 是这两者的平衡点。

**缩略图是防「自信地认错」的那道防线。** 词表吸附和唯一性去重都拦不住
`B-403` 被读成 `B-408`（两个都是合法编号），但用户瞄一眼缩略图就能发现。

### 查不到时高亮全部未识别碎片

「没找到」这句话零信息量——它可能意味着这块不在照片里，也可能意味着它就在
桌上只是没认出来，而这两种情况用户该做的事完全相反。系统本来就知道分割出
多少块、其中哪些读出了编号，差集免费可得。**把搜索范围从几百块塌缩到个位数。**

这条设计还有一个战略作用：它把「识别率不够高」从**功能缺陷**降级成了
**轻微不便**。即使识别率只有 85%，工具依然完全可用。

## 8. 本地引擎 + 局域网 Web

纯 Python 引擎（CLI 可独立运行），外面套一层薄 Web 界面，手机通过局域网访问。

识别管线依赖 OpenCV 和 PaddleOCR，本地装是五分钟的事，在云函数里是要处理
镜像体积和冷启动的事。第一版就上云会把一半时间花在跟部署环境搏斗上，
而不是解决「到底能不能认准这些小编号」这个真问题。

引擎与界面切干净，将来要上云换的只是外壳。

高亮图在**服务端**渲染，前端只做 `<img>` 加 CSS 变换的缩放平移。这让渲染
逻辑可以被单元测试覆盖，前端代码也从几百行降到几十行。

存储是每张照片一个 JSON。几百条记录，数据库纯属多余；JSON 可以直接打开看，
排查快得多。

## 9. 关键架构约束：识别器必须可替换

`recognize.OcrBackend` 是一个 `Protocol`，PaddleOCR 只是它的一个实现。
这带来两个性质：

1. **可测性** —— 除少数标记为 `@pytest.mark.ocr` 的集成测试外，所有测试
   注入假后端，**完全不加载 PaddleOCR**。测试几秒钟跑完，不依赖模型下载。
   这是整个方案里对迭代速度影响最大的单一决定。
2. **可退出性** —— §3 承认了纯本地路线有撞墙风险。换后端时只需实现一个
   `read(image) -> list[RawDetection]` 方法，上层分割、吸附、消解、渲染
   全部不动。

`recognize.LineOcrBackend` 是**可选**的第二个协议（`read_line`，跳过检测
模型只跑识别）。刻意做成独立协议而不是往 `OcrBackend` 里加方法——把它设成
必需会毁掉上面那个「只需实现 `read()`」的承诺。不实现它的后端一样能用，
只会走全量角度穷举。

---

## 10. 明确不做的事

- 自动解拼图、形状匹配、图案匹配
- 识别碎片正面图案
- 人工回填未识别编号（有价值，但需要一整套交互，第一版不做）
- 云端部署、公网访问、多用户
- 任意背景支持（明确要求深色纯背景，理由见 §4）
- 调用任何大模型或视觉语言模型（理由见 §3）
