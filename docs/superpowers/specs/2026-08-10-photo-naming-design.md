# 照片命名：让 photo_id 承载桌面区域

**日期**：2026-08-10
**状态**：已确认，待实施

---

## 1. 问题

用户把桌面固定分成四片区域，在手机上把四张照片改名为 `1` / `2` / `3` / `4`
来记住这个对应关系。上传之后名字变成了 `1786177906346` 这样的长数字，
「照片 2」这个含义丢了。

### 根因：名字在到达服务端之前就已经没了

链路只有两步：

1. 前端 `puzzlefind/static/index.html` 的 `form.append("file", file)`
   —— 文件名由浏览器从 `file.name` 填。
2. 服务端 `server.py:84` 的 `stem = Path(file.filename or "").stem`
   —— 原样采用。

而磁盘上落成的是 `1786177906346.jpg`。这个数是**毫秒时间戳**，换算为
04:31:46，而那份索引的 `created_at` 是 04:32:06 —— 只早 20 秒。
名字是**用户在手机上点选那一刻由浏览器现造的**，不是从改好的文件名来的：
安卓的相册选择器交给浏览器的是一个不带显示名的句柄，浏览器只好用时间戳兜底。

**所以「保留原文件名」这条路是死的。** `1.jpg` 从来没进过 HTTP 请求，
服务端无从保留。修法只能在别处。

### 同一个根因造成的第二个故障：刷新机制失效

`docs/design.md` §2 承诺「拿走碎片后重拍那张照片刷新索引」。但重拍同一片
区域会得到一个**新的时间戳 photo_id**，于是 `library.save_photo` 写出一个
新 JSON 文件，**旧索引原地不动地留着**。查询跨所有照片扫，很可能命中那份
过期的，而且每刷新一次就多积一份陈旧数据。

**没有稳定的标识，就没有「替换」这个动作。** 命名和刷新是同一个问题。

---

## 2. 目标与非目标

**目标**：`photo_id` 由用户指定且跨重拍稳定，从而
（a）查询结果里的「照片 X」能对应到桌上的一片区域；
（b）重拍同一区域是**替换**而非新增。

这是 `design.md` §7「屏幕位置 → 桌面位置」映射的第二层：高亮图解决
「在这张照片的哪里」，照片名解决「这张照片是桌上的哪儿」。

**非目标**：改名功能（区域固定，名字一次定好就不再改）；照片缩略图列表；
自动识别拍的是哪片区域。

---

## 3. 被否决的方案

**服务端自动顺序编号**（上传即分配「照片 1、2、3…」，按建索引先后）。
零交互，但编号由**上传时刻**决定而不是桌面位置决定——重拍区域 2 会拿到
「照片 5」。这正是当前问题的翻版，只是数字短了点。

**侧栏列表放缩略图，靠图认不靠名。** 零输入，而且「这张是桌上哪儿」用看的
比用读的直接。但它解决不了替换，查询结果那句「在照片 `1786177906346` 里」
照样没法读。它是本方案的补强而非替代，本次不做（YAGNI）。

---

## 4. 设计

### 4.1 `photo_id` 合法性 —— 新增 `library.sanitize_photo_id()`

`photo_id` 直接当文件名用：`data/index/{id}.json`、`data/photos/{id}.jpg`。
现在这个值来自 `Path(file.filename).stem`，而 `Path` 顺手剥掉了目录分隔符
（`Path("../../x.jpg").stem == "x"`），所以**现有代码是碰巧安全的**。改成读
一个自由文本字段之后这层意外的保护就没了，必须自己补。

放在 `library.py`：「photo_id 得能当文件名」本来就是这个模块的持久化约束，
而 `server.py` 给 jpg 命名时 import 它。

规则，违反即抛错（由 server 转成 HTTP 400）：

- 去首尾空白后非空
- 长度 ≤ 40 字符
- 不含 `/` `\` `:` `*` `?` `"` `<` `>` `|` 与控制字符（ASCII < 32）
- 不是 `.` 或 `..`
- 不是 Windows 保留名，大小写不敏感：`CON` `PRN` `AUX` `NUL`
  `COM1`–`COM9` `LPT1`–`LPT9`（这是 Windows 项目，`CON.json` 会当场炸）

函数返回去掉首尾空白后的字符串，除此之外**不做任何改写**。

**为什么拒绝而不是静默清洗**：静默把 `2/3` 改写成 `2_3` 会让用户以为存成了
自己输入的名字。名字是这个功能的全部意义，改写它等于把功能悄悄做坏。

### 4.2 API：`POST /api/photos` 加一个**可选**表单字段 `photo_id`

- 给了 → 过 `sanitize_photo_id`，作为 photo_id 与 jpg 文件名
- 没给 → 保持现有行为（`Path(file.filename).stem` 或 uuid 兜底）
- 非法 → 400，detail 说明违反了哪条

可选而非必填：curl 上传和现有 8 条 `test_server.py` 用例不受影响。

`GET /api/photos` 已经返回全部 photo_id，前端的区域选择器直接复用，
**不新增接口**。

**替换语义不需要新代码**：同 id 上传时 `server.py:86` 的 `cv2.imwrite` 覆盖
jpg、`library.py:59` 的 `write_text` 覆盖 json。id 一稳定，§1 那个刷新故障
自己就好了。

### 4.3 前端：上传前先选区域

`$("upload").onclick` 不再直接 `$("file").click()`，先展开一个面板：

```
这张拍的是哪片区域？
  [ 1 · 重拍替换 ]   [ 2 · 重拍替换 ]
  [ 3 · 重拍替换 ]   [ 4 · 重拍替换 ]
  [ ＋ 新的区域 ]                [ 取消 ]
```

- 已有照片各一个按钮，数据来自 `GET /api/photos`
- 按钮上直接写「重拍替换」——**语义前置，因此不设事后确认框**。重拍是常态
  操作（区域固定，绝大多数上传都是重拍已有的某一张），每次弹确认很烦
- 「＋ 新的区域」就地变成输入框，回车确认。输入一个**已存在**的名字与点那个
  区域的按钮完全等价——都是替换，不特殊处理、不报重名
- 库为空时只显示输入框
- 选定名字后才 `$("file").click()`；`onchange` 把名字随 `FormData` 一起发
- 上传失败时把服务端的 400 detail 显示出来

photo_id 是用户可控字符串，插进 DOM 一律用 `textContent`——页面里已有
这条约定（`buildPhotoSwitch` 的注释）。

查询结果那三处文案（`say()`、`cardWhere`、`buildPhotoSwitch`）**一个字都不
用改**：名字变好读了，句子自然就通——`照片 2 · 左上 · 置信度 0.99`。

### 4.4 存量数据

现有 4 份时间戳命名的索引由用户在网页上删掉、重新上传，**不写迁移代码**。
一次性的事，不值得留下只用一次的脚本。

## 5. 测试

沿用项目现状：Python 层单测，前端只做「页面里有没有这个钩子」的字符串断言。

**`tests/test_library.py`** —— `sanitize_photo_id`
- 合法名通过并去掉首尾空白（`" 2 "` → `"2"`）
- 空 / 纯空白被拒
- 含 `/` `\` `:` 等每类非法字符被拒
- `.` 与 `..` 被拒
- `con` / `COM1` / `LPT9` 被拒（大小写不敏感）
- 41 字符被拒，40 字符通过

**`tests/test_server.py`**
- 带 `photo_id=区域一` 上传 → 列表里的 photo_id 是 `区域一`
- **同一个 photo_id 连传两次 → `GET /api/photos` 仍只返回一条**
  （这条把刷新语义钉死，是本次改动的核心断言）
- 非法 photo_id → 400
- 不带 photo_id 上传 → 行为与现在一致（回归保护）

**`tests/test_server.py::TestFrontend`**
- 页面里含区域选择器的钩子，与现有那几条同风格
