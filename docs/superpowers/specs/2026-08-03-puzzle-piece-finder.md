## 1. 问题

用户手上有一套 **1000 块**的拼图，每块碎片背面印有编号，格式为**一个大写字母 + 短横 + 三位数字**（如 `A-304`、`B-403`、`C-220`）。字母组为 A/B/C/D 四组，每组 250 块。

拼图过程中，用户需要找到某个特定编号的碎片。桌面上散落着几百块碎片，肉眼逐块翻找极其低效。

**目标：** 用户拍照建立索引后，输入一个编号，系统在照片上高亮出对应的那块碎片，使用户能据此在实体桌面上定位它。

---

## 2. 使用场景

1. 拼图开始前，把某个字母组的碎片摊在**深色纯背景**上，分几次拍照（每张 40–60 块）
2. 逐张上传，系统建立「编号 → 碎片轮廓」索引（一次性开销，可能耗时数分钟）
3. 拼图过程中，手机浏览器打开局域网页面，输入编号，秒级得到高亮结果
4. 碎片被拿走或位置移动较多后，重拍变动的那张照片刷新索引

**关键洞察：真正的目标不是「在屏幕上标出碎片」，而是「让用户的手能在桌上找到它」。** 屏幕只是中介。这条洞察决定了高亮的设计（见 §5.7）。

## 4. 待澄清的事实 → **已由实拍数据结案（2026-08-03）**

> **结论先行：编号既不按字母分段，也不唯一。**
>
> `real3.jpg`（50 块，深色背景）跑完标定后：
> - **B 组实测跨 187–796**，610 个号位，远超「每组 250 块均分」的假设。
>   所以下面推测的「A=000–249、B=250–499…」**是错的**，四组根本不是分段的。
> - 更意外的是，**同一个编号会印在多块不同碎片上**：`B-506` 和 `B-652`
>   各出现在 3 块碎片上，另有 4 个编号各 2 块。50 块碎片只有 42 个不同编号。
>   这些碎片位于照片上相距 137–952 px 的不同位置，形状各异，
>   已排除「同一块被重复检出」。
> - 因此 §5 中「B-501 可能是误读」的猜测也被推翻：`B-501`/`B-512`/`B-513`
>   都是清晰碎片上读出的真实编号。
>
> **两个后果：**
> 1. `vocabulary.robust_ranges` 的离群剔除在真实数据上几乎空转
>    （区间宽到判不出离群），验收标准 4 实际没有防护力。真正拦住误读的
>    是唯一性规则。
> 2. 「每张照片内编号唯一」这条 Global Constraint 与现实矛盾。
>    **用户已决定维持现状**（见 §11 决策日志），即保留唯一性规则、
>    重复编号中只保留置信度最高的一块。**已知代价：**查询 `B-506` 时
>    只会高亮 3 块中的 1 块，且不提示还有其他同号碎片；被丢弃的那 2 块
>    会落进「未识别」集合，因此在查询任意未命中编号时会被青色圈出。

以下是结案前的原始记录，保留以说明当时的判断依据：

**各字母组的实际数字区间未知。** 用户确认整体范围是 000–999、每组 250 块，但不确定是否为均分（即 A=000–249、B=250–499、C=500–749、D=750–999）。

在样例照片中读到了疑似 `B-501`、`B-504`、`B-509`、`B-514`、`B-516`、`B-518`、`B-519` 等 5 开头的 B 组编号，若为均分规则则越界。两种解释：区间不是均分，或**这是全图识别的误读**（读图者是一个视觉模型，在整图上把小字读串了）。

**处理方式：不假设任何分组规则。** 词表就是 `{A,B,C,D} × 000–999` 共 4000 个候选，实际区间在运行时从识别结果自举（`vocabulary.bootstrap_ranges`）。Task 14 跑完真实照片后，日志里的自举区间会给出答案。

顺带一提，这次误读本身就是「不要用整图识别」这个决策的直接证据。

## 5. 设计决策

每条都记录了**选择**、**理由**和**被否决的替代方案**。

### 5.1 使用模式：建索引 + 查表

**选择：** 一次拍照建立完整索引，之后查询走本地查表（毫秒级、零额外成本）。支持重拍刷新，索引带 `created_at` 时间戳供 UI 提示可能已过期。

**理由：** 单次全图识别是重活（几十到几百块碎片的分割 + OCR），必须摊销，不能每次查询都跑。

**已否决：** 每次查询现拍现识别——把重活放在了延迟敏感的路径上。

**已知局限（接受）：** 拼图是动态的，用户每拿走一块索引就部分失效。缓解手段是分块拍照（§5.9），使刷新单张照片的成本足够低，用户才会真的去用。

### 5.2 形态：本地引擎 + 局域网 Web

**选择：** 先做纯 Python 引擎（CLI 可独立运行），再套一层薄 Web 界面，手机通过局域网访问。

**理由：** 识别管线依赖 OpenCV + PaddleOCR，本机 `pip install` 五分钟的事，在云函数里是要处理镜像体积和冷启动的事。第一版就上云会把一半时间花在跟部署环境搏斗上，而不是解决「到底能不能认准这些小编号」这个真问题。架构上引擎与界面切干净，将来要上云换的只是外壳。

**已否决：** 直接部署到云（CloudBase 等）、微信小程序、纯 CLI 无界面。

### 5.3 识别路线：OpenCV 分割 + PaddleOCR

**选择：** OpenCV 负责把碎片从背景中分割出来并给出轮廓多边形；每块单独裁剪放大后交给 PaddleOCR 识别；再叠加词表吸附与同图唯一性去重两层纯逻辑后处理。

**理由（用户拍板）：** 全本地、免费、离线、可离线迭代。

**已否决 1 — 整图直接交给视觉大模型：** 一张图里 100+ 个微小的、任意旋转的、浅灰低对比文本，是这类模型最弱的场景；且它不产出碎片轮廓，无法高亮。§4 记录的误读就是实证。

**已否决 2 — 分割后逐块交给视觉大模型：** 技术上可行且成本极低（实测估算：1000 块碎片用最贵的模型跑一遍不到 $3，用轻量模型约 $0.35，还可叠加 Batch API 五折与 prompt 缓存）。**是用户主动选择了纯本地路线**，接受了「省下的钱换成调参时间」这个交换。

**已知风险（接受）：** 风险从「成本」转移到「调参时间」。PaddleOCR 在 360° 任意旋转 + 浅灰小字上大概率需要几轮调试。缓解手段是把识别器做成可替换的协议接口（见 §6），撞墙时换后端不用重写整条链。

### 5.4 旋转处理：Pass A 打底 + Pass C 兜底

**选择：**
- **Pass A** — 整块裁剪图直接喂给 PaddleOCR，靠 DB 检测器自己输出旋转框并摆正
- **Pass C** — 置信度不足时，把裁剪图旋转 12 个角度各识别一次，取「能吸附到合法词表且置信度最高」的结果

**理由：** Pass A 零调参、代码几行；Pass C 用纯蛮力换掉了技术含量，而「必须命中合法词表」这个约束让蛮力的判据非常硬——错误角度几乎不可能凑出一个合法编号，误报率极低。代价只是 CPU 时间，而建索引是一次性的。

**已否决 — 自行估计文字角度（对墨迹像素做 PCA / `minAreaRect` 求主轴）：** 绕过了检测器这个单点，但阈值分离要调，碎片花纹、阴影、边缘都会污染主轴估计。这是三条路里调参成本最高的一条，而 Pass C 用蛮力实现了同样的效果。若 Pass A + C 的实测覆盖率仍不达标，这是下一个可选升级。

**执行注记：** `SWEEP_CONFIDENCE_THRESHOLD` 默认设为 `0.90`（很激进，宁可多穷举），依据是 §3 中记录的社区负面反馈——**Pass C 很可能不是兜底而是主力**。Task 14 会用真实数据给出该降到多少。

**2026-08-04 提速改造后的现状：**

实测单次 `PaddleOCR.predict()` 耗时 1.71 s，其中**检测模型占 1.485 s（92%）**，识别模型只占 0.129 s。原来的 Pass C 把整张裁剪图旋转 12 次、每次重跑一遍完整管线，等于把最贵的检测白跑 12 遍。

据此做了两件事：

1. **Pass C 提前退出**（`SWEEP_EARLY_EXIT_CONFIDENCE = 0.99`）——拿到足够高的合法编号就停。**实测 2.94x（385s → 131s），识别率不变**。这是本次全部的收益来源。
2. **新增 `"line"` 快路径**：复用 Pass A 已经拿到的检测框（`dt_polys`），按框裁出文字行、只重跑 rec 模型试正反两个朝向。机制在人工旋转的碎片上验证过（61 个有框样本 58 个与完整管线一致），**但在真实建索引里一次都没触发**——落进 Pass C 的碎片恰恰是 det 失败的那些，det 失败就没有框可复用。**这条路径目前是未经真实数据验证的代码**，去留需要一张碎片随机朝向的合格照片来裁决。详见调参日志。

**这次改造也部分推翻了 §5.4 对「自行估计文字角度」的否决理由。** 当初否决它是因为「调参成本高」，而这个判断隐含了「det 是免费的」这个前提。现在知道 det 占 92%，**前提已经不成立**，绕开检测模型是目前理论收益最大（约 13x）的杠杆。

### 5.5 分割前提：深色纯背景

**选择：** 要求用户把碎片摊在深色纯背景上拍摄。

**理由：** 这是整份 spec 里性价比最高的一条决策——**用 30 秒的行为改变，换掉一整天的调参**。样例照片背景是蓝白条纹毛巾，其中米白色区域与碎片背面几乎同色，任何基于颜色的阈值都分不出来，而那一带压着十几块碎片。换深色背景后，前景分离退化成一次 Otsu 阈值操作。

**已否决 1 — 支持任意背景：** 需要自适应阈值 + 边缘辅助 + 纹理特征，每一项都是要试的参数，且换光线可能又要重调。

**已否决 2 — 学习型分割（SAM 等）：** 对背景免疫，但几百 MB 模型 + 显著推理时间 + 又一个重依赖，对一个拼图辅助工具是杀鸡用牛刀。

### 5.6 粘连碎片切分：距离变换 + 分水岭，种子数由面积先验自动确定

**选择：** 用「团块面积 ÷ 全图碎片面积中位数」估计该团块含几块碎片，再二分搜索距离变换阈值使种子数恰好等于该值。

**理由：** 常规做法要手调「阈值取 0.5 还是 0.7」这类魔法系数；这里让每个团块自己找系数，用户完全不必参与调参。

**优雅降级性质（重要）：** 切分失败不会全盘崩溃。两块粘连被当成一块时，裁剪图里有两个编号，OCR 会读出两个，系统把两个编号都指向该区域——高亮范围偏大，但功能仍在。

### 5.7 高亮呈现：克制的压暗 + 描边 + 缩略图

**选择：** 非目标区域压暗到 **40–50% 亮度**（不是全黑），目标碎片保持原亮度并用高饱和洋红描边，同时显示识别到的编号文字和该碎片的裁剪缩略图。放大是可选按钮，不自动触发。

**理由：** 压暗比单纯描边在「一眼找到」上强得多——一张图里上百块碎片，一圈红边会被视觉噪声淹没。但**压得太暗会破坏空间定位能力**：用户把屏幕位置映射到桌面真实位置，靠的是周围碎片排布、背景纹理、桌沿这些参照物；压成全黑或自动放大到极致，用户会知道「它在这儿」却不知道「这儿是哪儿」。40–50% 是这两者的平衡点。

**缩略图的作用：** 防「自信地认错」。词表吸附和唯一性去重都拦不住 `B-403` 被读成 `B-408`（两个都是合法编号），用户瞄一眼缩略图就能发现。

**已否决：** 仅描边不压暗；全黑压暗；查询后自动缩放到目标。

### 5.8 识别失败处理：高亮全部未识别碎片

**选择：** 查询未命中时，把该照片中所有未识别的碎片一并高亮（用区别于命中的颜色）。

**理由：** 「没找到」这句话零信息量——它可能意味着这块不在照片里，也可能意味着它就在桌上只是没认出来，而这两种情况用户该做的事完全相反。系统本来就知道分割出多少块、其中哪些读出了编号，差集免费可得。**把搜索范围从几百块塌缩到个位数。**

**这条决策还有一个战略作用：** 它把「识别率不够高」从**功能缺陷**降级成了**轻微不便**。即使 PaddleOCR 只跑到 85%，工具依然完全可用。

**已否决 1 — 只回一句「没找到」。**

**已否决 2（推迟，非拒绝）— 人工回填：** 用户点击未识别碎片、手输编号、系统记住，识别率随使用爬向 100%。价值是长期的，但需要「点击选中 + 输入框 + 持久化」一整套交互，是第一版工作量最大的单点。**用户明确决定第一版不做。** 先用几次 §5.8 主方案，再判断值不值得。

### 5.9 拍摄粒度：每张 40–60 块，跨照片索引

**选择：** 分块拍摄，每张照片 40–60 块碎片，索引跨所有照片，查询结果告知在第几张。

**理由（这是识别率的最大杠杆）：** PP-OCR 的识别模型会把文字行统一缩放到固定高度（默认 48px）。决定成败的不是照片总像素数，而是**每个字符占多少像素**，而这由「一张照片塞多少块碎片」决定：

| 一张拍多少块 | 每块约占 | 字符高度 | 处境 |
|---|---|---|---|
| 250（一整组） | ~250 px | ~15 px | 勉强，大概率掉识别率 |
| 100 | ~400 px | ~25 px | 及格线 |
| 50 | ~570 px | ~35 px | 舒服 |

（按手机横向 4000 像素粗算。样例照片落在第一档附近。）

既然已经放弃了大模型、SAM 等所有兜底，**剩下唯一还能提升识别率的杠杆就是给 PaddleOCR 更清楚的输入**，而这个杠杆是免费的：多按两次快门换字符像素数翻倍。

**附加收益：** 只需重拍变动的那张照片。桌面上正在拼的区域动得最频繁，其他区域可能十几分钟没动过。重拍 50 块比重拍 250 块快得多，索引刷新的心理成本低，用户才会真的去用。

**已否决：** 一张全景拍完整个字母组。

### 5.10 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| PaddlePaddle | **CPU 版** (`paddlepaddle==3.3.1`) | `pip install` 直接可用；GPU 版需从 Paddle 自有源装且必须严格匹配 CUDA 版本，而本机是 CUDA 13（很新），大概率未覆盖。工作量本身也不需要 GPU——几百张小裁剪图过一遍识别模型，CPU 几十秒。之后若嫌慢，换 GPU 不影响任何其他代码。 |
| 后端 | FastAPI | 已装；`/docs` 在调试识别接口时好用 |
| 前端 | 单个 HTML，原生 JS | 不上框架、不上构建工具。界面只有三件事：传图、输编号、看结果 |
| 存储 | 每张照片一个 JSON + 原图 | 几百条记录，数据库纯属多余；JSON 可直接打开看，排查快 |
| 引擎边界 | 独立 Python 模块 + CLI | 调参时改一个数字跑一条命令，比每次起服务器传图快得多 |

**评审时的一处偏离（已确认）：** 高亮改为**服务端渲染**（复用被单元测试覆盖的 `render.py`），前端只做 `<img>` + CSS transform 的缩放平移。原定客户端 Canvas 合成。理由：渲染逻辑因此可测，前端代码从几百行降到几十行，缩放平移体验不受影响。

## 6. 关键架构约束

**识别器必须是可替换的协议接口。** `recognize.OcrBackend` 是一个 `Protocol`，PaddleOCR 只是它的一个实现。这带来两个性质：

1. **可测性** — 除两个专门标记的任务外，所有测试注入假后端，**完全不加载 PaddleOCR**。测试毫秒级跑完，不依赖几百 MB 的模型下载。这是整份方案里对迭代速度影响最大的单一决定。
2. **可退出性** — §5.3 承认了纯本地路线有撞墙风险。换后端时只需实现一个 `read(image) -> list[RawDetection]` 方法，上层分割、吸附、去重、渲染全部不动。

## 8. 非目标（明确不做）

- 自动解拼图 / 形状匹配 / 图案匹配
- 人工回填未识别编号（推迟到第二版，见 §5.8）
- 云端部署、公网访问、多用户
- 微信小程序或任何原生客户端
- 任意背景支持（明确要求深色纯背景）
- 调用任何大模型 / 视觉语言模型
- 学习型分割（SAM 等）
- 识别碎片正面图案
- **调用 PaddleOCR 云端 API**（`paddleocr.aistudio-app.com`，2026-08-04 评估后否决）

**关于云端 OCR API 的评估记录（免得日后重提）：**

它确实能省掉本地的 `paddlepaddle` 安装和 139 MB 模型下载，模型也是同一个
`PP-OCRv6`。但对这条管线不成立，三条理由：

1. **调用次数对不上。** 本管线是**逐块碎片**调 OCR：一张 50 块的照片实测约
   **266 次**调用（32 块直接命中 ×1，18 块进穷举 ×13）。而该 API 是异步作业制
   ——POST 拿 `jobId`，每 5 秒轮询——**每个作业的时间下限就是那 5 秒**。
   266 个作业 ≥ 22 分钟纯等待，还没算上传、排队和限流。本地现在是 9 分钟。
2. **改成整图一次调用会砍掉最大的杠杆。** 那样虽然只需 1 次调用，但送过去的
   字符高度是原始的约 20 px，而现在逐块裁剪放大到 512 px 后约 90 px——
   §5.9 认定这是识别率的最大杠杆。且官方示例只下载渲染好的 `ocrImage`，
   并未展示返回中是否含文字框坐标；没有坐标就无法把编号落到具体碎片上。
3. 与 §5.2/§5.3 用户拍板的「全本地、免费、离线」路线相反。

**真要提速，本地杠杆更大：** 那 234 次穷举调用占了总耗时的 88%，全花在 18 块
朝向不正的碎片上。拍照时把碎片摆正，每块从 13 次调用降到 1 次，免费且立竿见影。
